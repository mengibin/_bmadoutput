## 1. Goals and Scope

This addendum defines the architecture changes required to support Runtime multimodal data extraction:

1. Chat panel drag-and-drop ingestion of files/folders.
2. `media.extract` as a first-class function-call tool directly exposed to LLM.
3. Schema-driven structured extraction (`schema` provided by user or generated by LLM from intent).
4. Configurable multimodal LLM profile with explicit capability checks and error handling.
5. `fs.read` retained only as compatibility fallback for binary inputs.

MVP formats: `.pdf`, `.png`, `.jpg`, `.jpeg`, `.webp`.  
Phase-2 extension: `.ofd` via conversion pipeline.

## 2. Key Architectural Decisions (AD-MULTI-*)

### AD-MULTI-01: `media.extract` is first-class

- **Decision**: `media.extract` is directly available in the tool registry and can be called by LLM without a preceding `fs.read`.
- **Rationale**: Binary/fixed-layout documents should not pass through text-first read paths.
- **Consequence**: Tool policy and system prompt must explicitly prefer `media.extract` for binary content.

### AD-MULTI-02: `fs.read` becomes fallback-only for binary

- **Decision**: `fs.read` remains available for text files and compatibility scenarios.
- **Rationale**: Existing workflows/tools still rely on `fs.read`.
- **Consequence**: For binary input, `fs.read` must return structured hint metadata (not garbled text), guiding to `media.extract`.

### AD-MULTI-03: Dedicated multimodal model configuration

- **Decision**: Runtime settings provide a dedicated `Multimodal LLM` config (provider/baseUrl/model/apiKey/timeout), decoupled from text model selection.
- **Rationale**: Teams may use different models for reasoning vs. visual extraction.
- **Consequence**: Runtime must validate model capability before invoking `media.extract`.

### AD-MULTI-04: Schema planning is part of extraction flow

- **Decision**: `media.extract` accepts optional `schema`; if absent, schema may be generated from `instruction/schemaIntent`.
- **Rationale**: Keeps extraction contracts stable while supporting intent-first usage.
- **Consequence**: Output must include `schemaUsed` and `schemaSource` for auditability.

### AD-MULTI-05: Provider capability errors are explicit

- **Decision**: Unsupported multimodal model returns `LLM_MULTIMODAL_NOT_SUPPORTED`.
- **Rationale**: Deterministic failure mode for UX and workflow retries.
- **Consequence**: UI and run logs can branch on stable error code.

## 3. Target Runtime Components

### 3.1 Renderer (Chat Panel)

- `ChatInput` supports dragging:
  - single file
  - multiple files
  - folder (recursive discovery handled in main process)
- Attachments are carried as structured payload (path, name, mime hints, root context).

### 3.2 Main Process Services

- `AttachmentIngestionService`
  - resolves dropped files/folders
  - recursively enumerates supported files
  - normalizes alias paths (`@project/...`)

- `MultimodalCapabilityService`
  - validates current multimodal model configuration
  - checks capability matrix per provider/model

- `SchemaPlanningService`
  - if `schema` missing, generates schema draft from intent
  - validates draft before extraction call

- `MediaExtractionOrchestrator`
  - dispatches image/PDF extraction
  - handles PDF page iteration
  - aggregates structured records for output

### 3.3 Tool Host

- Add new function tool: `media.extract`
- Keep `fs.read` behavior for text; binary access returns structured fallback hints.

### 3.4 LLM Adapter

- Add multimodal request mapping per provider.
- Keep single internal extraction contract (`MediaExtractArgs`) and adapt outward per provider API shape.

## 4. API and Data Contracts

### 4.1 Chat Input Contract (incremental)

```ts
interface ChatAttachment {
  path: string;         // alias or absolute
  name: string;
  mimeType?: string;
  isDirectory?: boolean;
}

interface ChatSendPayloadV2 {
  // existing fields...
  input: string;
  attachments?: ChatAttachment[];
}
```

### 4.2 `media.extract` Tool Contract

```ts
interface MediaExtractArgs {
  path: string;
  instruction: string;
  schema?: object;
  schemaIntent?: string;
  page?: number;
  strict?: boolean;
  documentTypeHint?: string;
}

interface MediaExtractResult {
  ok: boolean;
  mime?: string;
  path?: string;
  page?: number;
  data?: Record<string, unknown>;
  schemaUsed?: Record<string, unknown>;
  schemaSource?: 'provided' | 'generated';
  confidence?: number;
  warnings?: string[];
  error?: { code: string; message: string; details?: unknown };
}
```

### 4.3 Error Codes

- `LLM_MULTIMODAL_NOT_SUPPORTED`
- `MEDIA_UNSUPPORTED_FORMAT`
- `MEDIA_DECODE_FAILED`
- `MEDIA_SCHEMA_INVALID`
- `MEDIA_EXTRACTION_FAILED`

## 5. End-to-End Sequences

### 5.1 Primary Path (Direct `media.extract`)

1. User drags files/folder into chat panel.
2. Runtime builds candidate file list.
3. LLM invokes `media.extract` directly for each file/page.
4. If schema absent, schema is generated from intent and applied.
5. Runtime aggregates results and writes `@project/artifacts/extracted-data.json`.

### 5.2 Unsupported Model Path

1. `media.extract` requested.
2. Capability check fails.
3. Runtime returns `LLM_MULTIMODAL_NOT_SUPPORTED`.
4. UI prompts model reconfiguration; run can be retried.

### 5.3 Compatibility Path (`fs.read` on binary)

1. LLM calls `fs.read` for binary path.
2. Tool returns structured hint (`mime`, `path`, suggested `media.extract`).
3. LLM retries via `media.extract`.

## 6. Security and Guardrails

- Maintain mount sandbox: `@project/@pkg/@state`.
- Keep `@pkg` read-only.
- Enforce file type and size limits for extraction.
- Validate all generated/provided schemas before strict extraction.
- Do not log raw binary payloads; logs store metadata only.

---

## 7. Observability

For each file/page extraction, log:

- `runId`, `conversationId`, `sourceFile`, `page`
- selected model/provider
- schema source (`provided`/`generated`)
- latency, outcome, error code (if any)

Recommended metrics:

- extraction success rate
- schema validation pass rate
- unsupported-model error rate
- p95 extraction latency per format
